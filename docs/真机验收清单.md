**核包脚本**（① 那套，`pwsh` 里跑；`$ipa` 换成要核的那个包）：

```powershell
$ipa = 'D:\VidLog-Mobile\dist\vidlog-ios-unsigned-19\VidLog-unsigned.ipa'
$work = "$env:TEMP\vidlog-unpack"
Add-Type -AssemblyName System.IO.Compression.FileSystem
$zip = [System.IO.Compression.ZipFile]::OpenRead($ipa)
$e = $zip.Entries | Where-Object { $_.FullName -like '*App.framework/App' }
[System.IO.Compression.ZipFileExtensions]::ExtractToFile($e, "$work\App", $true)
$zip.Dispose()

# 关键：把字节 1:1 映成字符来搜（Latin-1），否则中文会被当字节流搜坏
$latin = [System.Text.Encoding]::GetEncoding(28591)
$text = $latin.GetString([System.IO.File]::ReadAllBytes("$work\App"))
function FindIt([string]$s) {
  $text.Contains($latin.GetString([System.Text.Encoding]::Unicode.GetBytes($s)))
}
# 该在的、该不在的，都过一遍
FindIt '搜索单号或日期'   # True
FindIt '录像记录'         # False
# ⚠️ 顺手跑一条**从来不存在**的串，它必须是 False
FindIt 'ZZZ_从未存在过_ZZZ'   # False
```

> ⚠️ **`GetEncoding(28591)` 那两处不要动。** 它在这里的用处是把**每个字节**
> 1:1 映成一个字符 —— 只有这样 `Contains` 才是真正的**逐字节**子串搜索。
> 用默认编码去搜中文，结果会因为被解码成别的字而**假阴性**，
> 而那看起来就像「这个包是旧的」。

> ⚠️⚠️ **不要用 `-in` / `-contains` 当子串包含。** 它们是**集合**运算符：
> 右边是字符串时会被当成**一个元素**，于是 `'甲' -in $text` 等于问
> 「整个 $text 是不是就等于『甲』」—— **永远 False**。
> 而它不会报错、看起来跑得好好的，只会让你以为**每个包都是旧的**。
> 这一条是 2026-09-23 实际踩到的：同一段脚本换个运算符，
> 已知在包里的 `未命名机位` 也被报成 False。
> **所以脚本里必须留一条「从来不存在」的串做反证** ——
> 它要是 True，说明搜索这层坏了，而不是包变了。

## 1.8 ★ 目标跟踪（2026-09-21 新补）

> 规格 §3.3.1 的「同码**离场**后再入场**并静止 2 秒**」。
>
> ⚠️ **本节 2026-09-22 晚些重写过。** 那个「静止」**不是**设置页里的静止档位，
> 而是**这个模式自己固定的 2 秒**（档位设成「关闭」时也照样生效）。
> 下面这条已把前置改成档位「关闭」，**照旧能看到它停** —— 那正是要证的。
> 同时，这个模式下**复扫同码也会停**（2026-09-21 那条「复扫不停」的裁定已作废）。
>
> 两处区别的对照表与详细判据在 **§1.16 ② 与 ③**，本节只留「跟踪」那一半。

- 模式：**扫码静止**，静止档位：**关闭**（⚠️ 故意的：这样「它停了」就顺带证明了这 2 秒不来自档位）
- 时长兜底：**关闭**（否则它会先触发，验的就不是它了）
- 点【开始工作】，拿面单 **A** 放进取景框扫到开录
- 把 A **整个拿出画面**（或者翻过去让条码看不见），**等 3 秒以上**
- 把 **A 放回**取景框
- 之后**手不要碰手机、画面里别再出现别的条码**，等 2 秒

**通过的判据（按顺序出，缺哪个就是哪一环坏了）**：

| 该出现的日志 | 说明它坏了的话 |
|---|---|
| `📷 扫到 A` | 识码本身没工作 |
| `📦 包裹离开取景框` | **跟踪没认出离场** —— 后面那两条都别指望了 |
| `📦 包裹回到取景框` | 认出了离场，但没认出「它回来了」 |
| `👁 画面静止 —— 静止计时从现在起算` | **静止计时那一路没跑起来**（档位是「关闭」，但这 2 秒照样该计） |
| 约 **2 秒**后 `停录 · 画面静止` | 跟踪是好的，**静止门槛坏了** |

> ⚠️ **2 秒在真机上要「拿捏」**：放回去之后手要**彻底离开画面**（画面里有人动
> 就不算静止，那 2 秒会推迟）。用掐秒表的方式量不准，**看「是不是很快就停了」**即可。

**另外验一下「复扫同码也停」**：重新开一段，扫 A 开录，**不动它**、直接再扫一次 A ——
**应当停止**，滴 + 念「停止录像」。
（⚠️ 2026-09-21 曾裁定「复扫不停」，**该裁定作废**。见 `实现决策.md` §1.2 与 §22。）

> ⚠️ **拿开面单要真的拿开。** 跟踪的判据是「多久没再见到那个条码」（2 秒），
> 面单被手挡住、或者只是挪到画面边上但还在识别区内，都不算离场。
>
> ⚠️ **A 拿开之后别再扫到别的单号** —— 扫到 B 不会取消 A 的离场（有测试锁），
> 但会让现场变乱、不好判断。

**通过的判据**：

① 本机身份

> ⚠️ 这一条**验不了**「未命名1 / 未命名2」那个编号 —— 它属于 M5 电脑端的设备表，

- 放面单 **B** 进框 → ✅ **A 那一段立刻收尾入库**，B **紧接着开始录**
  （中间不该有「停下来等人点一下」的空档）
- 再放 **C** → 同样的动作，A、B 都已入库，C 在录
- 点【结束】→ ✅ 最后一段（C）也入库
- 去**备份页/视频记录**数条数：**A、B、C 各一条**，不是「一条长长的录像」

| 要盯的 | 现象 |
|---|---|
| ✅ | 换段时**不播**「面单不同」（换件是正常路径，报了反而盖住下一件的开录播报） |
| ⚠️ | 换段**空档 1~3 秒**是**已知的**，不打算修。丢的是**打点对齐，不是画面** —— 原件是连续录的，一帧都不少。真机上要是看出来偏移明显，记下来 |
| ⚠️ | **连续扫下没有错码保护了**：画面里恰好能读到的**别的条码**（邻件、货架标签）会**当场切断**当前录制。什么都没丢（上一段已入库、新段已开），代价是**一件包裹被劈成两条会话**。**这是决策，不是 bug** —— 但真机上要是频繁发生，说明得加消抖 |

- ⚠️ **另两个模式（同码停 / 扫码静止停录）必须保持原样**：扫到别的单号**只提示、不换段、不停录**。
  顺手回 §1.5 把这两条各跑一遍 —— 换段式**只对连续扫生效**。

### ④ 面单进框自动对焦 + 放大两秒

> ⚠️ **2026-09-22 改了：放大从「瞬间跳」改成「平滑推进 / 推远」。**
> 这一条要重跑。

- 把面单放进取景框 → ✅ 画面**推近**（**看得出是个过程，不是瞬间跳大**）到 2 倍
- ✅ 约 **2 秒后**再**推回**原倍率（**同样是个过程，不是瞬间跳小**）
  —— 那 2 秒指的是**推到位之后**保持的时间，路上走的那一小段不算在内
- ✅ 对焦：面单上的字**变清楚**（不是一直虚着）
- ⚠️ **手感的判据就是这一条**：只要是「唰地跳过去」就是没生效。
  真机觉得推得太快或太慢，改 `zoomRampRate` **那一个数**
  （`CameraSegmentRecorder.swift`，3.0 ≈ 1×→2× 走 0.33 秒）
- ⚠️ 已经放大到上限的设备：放大到设备上限就停，**不是**一定要 2 倍
- ⚠️ 你自己**先拖表盘放大到 3 倍**，再让面单进框 → ✅ 画面**不会先缩回去**再放大
- ⚠️ 自动放大的那 2 秒里**拖表盘** → ✅ 表盘**立刻**生效（表盘本身仍是瞬时的，
  要跟手），**2 秒后不该再跳回去**（跳回去 = 表盘看起来像失灵）
- ⚠️ **手输兜底输单号不触发放大**（画面里没有面单，放大一下只会让人以为相机坏了）
- ⚠️ **表盘显示的是你自己设的倍率**，不是那 2 秒里的瞬时值 —— **这是有意的**，别当 bug 记

> 表盘本身（【对焦】按钮、刻度、0.5×、拨轮声、滑动对焦）见 **§1.10**。

### ⑤ ★ 发货 / 退货写进了标签表（这一条要连电脑端一起看）

做完一段录像之后：

- 用「文件」App 进 App 自己的目录，跟 `index.jsonl` **同一层**，找 **`labels.jsonl`**
- 每录一段就该**多一行**（一个会话 N 段就 N 行，每行挂在自己的 evidenceId 上）
- 一行长这样（**键名是 PascalCase，不是 camelCase —— 不是笔误**，见下）：

```json
{"EvidenceId":"sess-...-000","Key":"business-type","Value":"outbound","UpdatedAt":"2026-09-22T..."}
```

- ✅ 发货栏录的 → `"Value":"outbound"`；退货栏录的 → `"Value":"return"`
- ✅ 「发货↔退货」切完栏**接着录**（不重建编排器）→ 新那段是**新栏的值**，不是旧栏的
- ★ **连电脑端一起验**：把这份 `labels.jsonl` 拷到电脑端，看它认不认这两条标签
  —— **这是唯一能证明「两端写的是同一份东西」的办法**，本机测不出来

| 要盯的 | 为什么 |
|---|---|
| ⚠️ 电脑端**认不出来** | 两端的键名/取值是**读代码**核对的，不是跑出来的。认不出来就是这里出了偏差，把两边原文都记下来 |
| ⚠️ 杀 App → 重启 | 重启会自动收尾孤儿，**标签也要补上**。走 §1.2 那条流程后，检查 `labels.jsonl` 里有没有那一段 |
| ⚠️ 老版本的清单 | 老 `session.json` 里**没有** `businessType` 字段 → 那种会话收尾时**不写标签**（宁可不写也不猜）。这是对的 |
| ⚠️ 标签没写进去、但录像正常 | **也是对的** —— 标签是「可修正的备注」，写标签失败**不算收尾失败**。宁可少一个标签，也不能少一条录像 |

## 1.16 ★ 出声 + 扫码静止改判 + 实时时间与完整单号 + 对焦收进工作期间（2026-09-22 第三批）

规格：母仓 `docs/01-行为规格书.md` §3.3.6（新）、§3.3.1、§3.3.2、§3.1.6、§3.2.6。

### ① ★ 声音：先「滴」一声，再念一句话

**六行表（规格 §3.3.6），逐条对**：

| 你做的动作 | 该听到什么 |
|---|---|
| 点亮【开始】 | 只念「**开始工作**」，**不滴** |
| 点亮【结束】 | 只念「**停止工作**」，**不滴** |
| 面单进框、识别到单号开录 | **滴** + 念「开始录像」 |
| 连续扫：换上第二件面单 | **滴** + 念「开始录像」（**没有**「停止录像」） |
| 复扫同一张面单停录 | **滴** + 念「停止录像」 |
| 录着的时候扫了**别的**面单 | **滴** + 念「面单错误，请扫描正确面单」 |
| 画面静止自动停 | **什么都不念**（正常，不是坏了） |
| 时长兜底自动停 | **什么都不念**（正常） |

**要盯的**：

| 要盯的 | 为什么 |
|---|---|
| ⚠️ **把「设置 → 声音与触感 → 键盘反馈」关掉，再试一遍** | 那个「滴」**必须照响**。它是 `AudioServicesPlaySystemSound`，不走键盘反馈开关。（拨轮声是另一回事，它本来就该跟着键盘反馈走） |
| ⚠️ 滴和念**叠在一起** | 说明 0.3 秒的间隔没生效。真机上是「滴——开始录像」，不是「滴开始录像」 |
| ⚠️ 连续快扫两件 | 第二句**顶掉**第一句，不是排队把第一句念完。排队的话操作员听到的是上一件的话 |
| ⚠️ 点【开始】/【结束】时听到了「**开始录像**」 | 那是回归 —— 点【开始】时**还没扫到面单、还没在录**，说「开始录像」是假话。必须是「工作」 |
| ⚠️ 换段时听到了「停止录像」 | 换件是正常路径，中间插一句「停」会让人以为录断了 |
| ⚠️ 整段操作**一点声音都没有** | 先看设置页【语音播报】开关是不是关的。**关掉时提示和日志照旧**，只是不出声 |

### ② ★★ 扫码静止停录：**两条判据都要验**（本批改动的正主）

**这一条是最需要认真验的**：它同时压着两处推翻 ——
复扫同码（2026-09-21 裁定作废）与那个 **2 秒**（我上一版理解反了，已按需求方原话改回）。

> ⚠️ **前置的关键：静止档位设成「关闭」。** 这样「它停了」就**同时**证明了
> 这 2 秒**不来自设置页的档位** —— 只写「静止两秒会停」是证不出这一点的。
> （需求方原话：「扫码静止停录和设置里的静止停录意义并不相同……两者不冲突。」）

**②‑A 复扫同码**

- 模式：**扫码静止停录**，静止档位：**关闭**
- 扫 A 开录（要**滴 + 念「开始录像」**）
- **把 A 再放进框里**让它识别到 → **应当停录**（滴 + 念「停止录像」）

**②‑B 离场 → 再入场 → 静止 2 秒**（⚠️ 前置同上，档位**关闭**）

- 扫 A 开录
- 把 A **整个拿出画面**，等 3 秒以上（挂到跟踪那条「包裹离开取景框」日志）
- 把 A **放回框内，然后手离开画面、别再动**
- **应当很快就停**（约 2 秒）→ 日志 `停录 · 画面静止`
- 停之前应当先出现一行 **`👁 画面静止 —— 静止计时从现在起算`** ——
  它是这 2 秒的**起点打点**。⚠️ **档位设成「关闭」时它照样要出现**：
  那条日志的闸问的是「现在有没有在计静止」，**不是**「档位开没开」
  （按档位判的话，这一模式下这条日志会被整个吃掉，而那正是最需要它的场合）。
- ⚠️ **停完之后**：相机**仍然开着**、按钮**仍然是红的【结束】**、
  状态是「已收尾 · 可继续扫下一件」—— **不是**退回「点按钮才开始」的工作前状态。
  再扫一张面单应当**照常开录**，不用重新点【开始】。

**要盯的**：

| 要盯的 | 为什么 |
|---|---|
| ⚠️ 复扫 A **没停** | 没改到位。**但先确认扫描闸真的认了那一下** —— 面单要在框内、清晰 |
| ⚠️ ②‑B **拿开后不回来也停** | 门槛没生效。「离场→再入场」是**必须**的，少了它每段录制都会在开录 2 秒后自己结束 |
| ⚠️ ②‑B **一直不停** | 2 秒没生效（或档位被当成了判据）。这条**必须**在档位「关闭」下也能停 |
| ⚠️ 停下来之后**相机被关了 / 要重新点【开始】** | 那是把这条接成了「结束工作」。需求方原话：「**而不是彻底停止工作**」 |
| ⚠️ 复扫 A 之后**又自动开录了** | 不该发生 |
| ⚠️ **在嘈杂/有人走动的现场试** | 静止判的是**画面**，不是那张面单本身。背景里有人搬东西时那 2 秒会推迟 —— **已知并接受**，不是 bug |

### ③ ★ 两个模式的区别（**从一处变成两处**）

2026-09-22 晚些之后，扫码静止停录与同码停分得**更开**了：

| 模式 | 复扫同码 | 要静止多久 | 什么时候开始计 |
|---|---|---|---|
| 同码停 / 连续扫 | 停 / 不停 | **设置页的档位**（关闭 / 2~5 分钟，「关闭」= 整条不生效） | 直接计 |
| 扫码静止停录 | **停** | **自己的 2 秒**（**不读档位**，档位「关闭」也生效） | **必须「包裹离场 → 再入场」之后** |

> ✅ **「要不要合并」这个问题已经问过需求方了：不合并。**
> 上面那两处区别就是他不合并的理由 —— 少了它们，这个模式就只剩一个名字了。
>
> ⚠️ **副作用，真机要盯**：「包裹回来」通常**同时**就是一次复扫，
> 所以那条 2 秒判据只在「包裹回来了、**但面单没正对着取景框**」时才轮得到
> （相机认得到 → 算入场；扫描闸不采纳 → 不算复扫）。
> 想单独验 2 秒判据的话，就是 ②‑B 那个姿势：**面单拿出去再放回来**。

### ④ 错码保护（§1.5 的判据这次加强了）

- 模式：**同码停** 或 **扫码静止停录**
- 扫 A 开录 → 扫 **B**（另一张面单）

**通过的判据**：
- **滴** + 念「**面单错误，请扫描正确面单**」（⚠️ 措辞**变了**，旧版是「面单不同」）
- **不停止录制** —— 这一条是关键，录还在继续
- 再把 **A** 放进去 → **滴** + 停录，念「停止录像」

### ⑤ 采集页画面上方的实时时间（白色描边字）

1. 进【发货】或【退货】栏
2. **应当看到**：画面**正上方居中**有一行 `2026/09/22 18:23:12`

**通过的判据**：
- 格式**正好**是 `年/月/日 时:分:秒`，年月日之间是 `/`，时分秒之间是 `:`
- **每秒都在跳**（⚠️ 这一条 widget 测试测不了，只能靠眼睛）
- **白色字外面有一圈黑描边** —— 把手机对着**白墙 / 白面单**再确认一次：
  纯白背景下没有描边的话，字会完全看不见
- ⚠️ **让手机显示的时间与旁边一台手机/手表对一下**：最多差 1 秒。
  **差将近 1 秒（显示的是上一秒）是 bug** —— 秒针没对齐整秒
- ⚠️ 改一下手机的**系统时间**，这一行应当**立刻跟着变**
  （它读的是墙钟；这与录像时长用单调时钟**不矛盾**，用途不同）

### ⑥ 完整单号（红色，在时间下面一行）

- 扫到面单之后，时间`下面一行`出现**红色**的完整单号

**通过的判据**：
- 颜色是红的
- **完整**：从头到尾一位不缺、**没有 `…`**。⚠️ 拿面单上的原文**逐位对一遍**
  —— 这是这一项存在的全部意义。被截断的单号看起来仍然像一个完整单号，
  抄下来就是错的，而且没人会怀疑
- 单号特别长时**换行**，不是省略号
- 停录之后那一行消失

### ⑦ ★ 对焦只在「点了开始之后、点结束之前」触发

- 进【发货】栏（相机自动开，**这时还没点【开始】**）
- **把面单放进框里再拿出来**

**通过的判据**：
- ⚠️ **画面不该推进再缩回来** —— 这时只是相机开着，不该对焦

- ⚠️ 点【结束】之后，**【对焦】按钮和表盘应当整个消失**（不是变灰、不是点了没反应）

## 1.17 ★ 备份状态小标（2026-09-23 新做，M5）

> 规格 §3.4.3 ★ —— 这一条来自**一次真实故障**：原系统上传失败后进终态、
> 永不重试，用户完全不知道数据没传上去。
>
> 前置：电脑端要开着（M3 的回放服务已经在跑），两端连同一个局域网，
> 并在手机端【电脑备份】那块点过【配对电脑】。

### ① 没配对时说真话

- 不动任何设置，进【备份】栏

**通过的判据**：
- 【电脑备份】那块明写**「还没和电脑端配对，录像传不上去」**，
  并且补一句**「这些录像现在只在这台手机上，手机丢了就没了」**
- ⚠️ 一个「离线」「未连接」之类的字都**不该**出现 ——
  那会让人以为「配过对、只是没连上」，而去改地址
- 【立即备份】是**灰的、点不动**，而**为什么点不动**就写在它下面那行

### ② 配对之后小标开始动

- 点【配对电脑】→ 把电脑端显示的 6 位数字填进去

**通过的判据**：
- 配对成功后【立即备份】变成可点
- 录一段（让它自己收尾入库）→ 回【备份】栏 → 那一条的小标应当自己
  走完 **未备份（灰）→ 备份中…（蓝）→ 已备份（绿）**
- ⚠️ **不点【立即备份】也该自己传** —— 收尾入库的那一刻就进队列了

### ③ ★★ 六段传到五段，必须说「备份失败」

**这一条是整页存在的全部理由。**

- 录满 30 分钟（5 分钟一段 → **6 段**）
- 让前 5 段传完
- 第 6 段开传之前，**把电脑端关掉**（整台机器关，或者断网）

**通过的判据**：
- 那一条的小标读作 **「备份失败」（红）**，**不是「已备份」**
- ⚠️ 小标是**可以点**的（`ActionChip`）：点开是「为什么没传上去」
  和一个【再试一次】
- ⚠️ **绝不能出现「已备份」而实际只传了 5 段** ——
  用户会照着那句话把手机上的原文件删掉

### ④ 到顶之后不再自动重试，但人还能救

- 接着上一步，把电脑端开着，然后**不管它**，等退避试满

**通过的判据**：
- 失败详情里写的是**「试了 N 次都没成功」**，不是「可以再试一次」
  —— 后者会让用户以为它还在努力
- ⚠️ **不再自己重试**（电脑端那边看请求数，过几分钟不再涨）
- 点【再试一次】→ **立刻**重传，不等退避；成功之后小标变绿

### ⑤ 杀进程不丢重试次数

- 在退避期间**杀掉 App**（不是退出，是从后台划掉）
- 重新打开

**通过的判据**：
- ⚠️ 它**没有**从「第 0 次」重新开始。重启一次就清零的话，
  「有限次重试」实际上变成了**无限次** —— 一条永远传不上去的录像
  会让手机一直重试，而用户看不见任何异常

### 本次**没能自动验证**的（只能真机看）

## 1.21 ★ 扫码连接（2026-09-26 新做，M5 入网改扫码）

### ③ 同意 / 拒绝两条路

- **同意**：电脑端弹窗上点【同意】→ 手机显示「连接成功」，紧接着弹出**改机位名**
  （12 格上限，见 §1.20）。改完名字之后，电脑端的设备列表上应当显示**新名字**。
- **拒绝**：电脑端点【拒绝】→ 手机**当场**说「电脑端拒绝了这次连接」，

- 生成的码放**超过 5 分钟**再扫：同一句话。
  ⚠️ 不能说「这是程序的问题」—— 那句话在这一版里已经改成能说清下一步的了。

让你手填地址。填对之后**不用重新扫码**就能连上 ——
**换的只是地址，令牌还是刚扫的那一张**。

### ⑥ ⚠️ 预览是黑屏吗（**只有真机知道的一条**）

### ① ★★ 这台手机真能跑哪一档（本批的正主）

## 1.26 ★ 水印（2026-09-27 新做，规格 §3.6.2）

**这一条的验收动作本身就在导出的成品上做** —— 在 App 界面上看不出来，
必须**把录好的视频导出来、拿系统播放器打开看那两行**。

规格原话：「水印**烧进视频画面**，不是只在界面上叠加 —— 导出件、分享件**都带着它**」；
「**所见即所得**：屏幕上看到的那两行，就是录进文件的那两行。
对不上就没法验收 —— 也正因如此，这一条的验收要在**播放导出的成品**上做。」

### ① ★★ 两行都在，而且位置对（先做电脑端，它最好验）

电脑端拿本机摄像头录一段（10 秒就够），用系统播放器打开。

- ✅ 画面上方**居中**有一行白字 `2026/09/27 12:34:56`（**带黑描边**，压在白面单上也看得见）
- ✅ 它**下面**一行是**红色**的**完整**单号
- ✅ 两行都在画面**最上方**，**不挡中间的取景范围**
- ✅ **秒在走**：拖动进度条，每一秒的字都不一样

> ⚠️ **不要只看第一帧就下结论**：字幕是按秒生成的，第一帧对不代表后面都对。

### ② ★★ 「不得取自墙钟」—— 录到一半改系统时间

**这一条是水印唯一真正要防的事**（规格 §3.6.3）。

- 开始录 → 录到 10 秒左右，**把系统时间往前调 1 小时**（不是时区）→ 继续录到 30 秒
- 导出，用播放器打开**中间那一段**
- ✅ 画面里的时间是**连续接着走的**（12:34:56 → 12:34:57 → …），**没有跳**
- ⚠️ **跳了一小时** = 水印读了墙钟 ⇒ 这一条没做成

### ③ 完整单号不截断

- 拿一个**很长的单号**（或手输一串 20 位的）
- ✅ 水印上那一行是**完整**的（不会被省略号或截断吃掉尾巴）
- ⚠️ 拿面单原文**逐位对一遍** —— 截断的单号看起来仍然像一个完整单号
  （与 §1.16 ⑥ 界面上那一行为同一个理由）

### ④ ★★ 手机端：**安卓那一路是独立的**（本批风险最高的一处）

> ⚠️ 安卓这次**插了一层 GL**（相机 → 外部纹理 → GL 合成 → 编码器）。
> 原来相机是**直接**写编码器的输入 Surface 的，所以这条管道是新加的。
> 「相机 + GL + 编码器」出问题时，症状通常是**一块黑屏或一帧不出**。

- 安卓上录一段 → ✅ **有画面**（不是黑屏）、播放正常
- ✅ 水印两行都在、红字是红的
- ⚠️ **黑屏 / 录不出东西** = GL 那一路坏了。App 会报一句
  「水印没启用（画面合成起不来），录像照常」并**退回直连通路**（无水印但能录）——
  看到那句就说明降级生效了，把日志记下来
- ✅ iOS 上同样录一段、同样看那两行

### ⑤ 所见即所得

- 录制页上方那行时间（§1.16 ⑤）与水印第一行**是同一个时刻**（差不超过 1 秒）
- ⚠️ 对不上说明两处各读了一个源（界面读墙钟、水印读可信时钟）——
  **这是设计之外的偏差**，记下来

### 本次**没能自动验证**的（只能真机看）

| 项 | 为什么 |
|---|---|
| **字有没有真的画进帧里** | 开发机没有摄像头、也不跑模拟器；能自动测的只有「文字格式」（8 条）与「开录时带过去的单号与可信时刻」 |
| **红字是不是红的** | 颜色要靠眼睛看（电脑端那边至少验到了「字幕文件里写的是红」，帧里是不是红的仍然只能看） |
| **安卓那条 GL 通路** | 它是本批风险最高的一处：**改了采集管道本身**，而安卓整条链路至今没上过真机 |
| **水印位置会不会挡到别的东西** | 「不遮挡取景框」是几何判断，得看实际画面 |
| 4K 下的位置与字号 | 字号按画面高度比例算，4K 下应当更大 —— 要真机确认不失真 |

> ✅ 能自动测的那部分已经测了：Dart 侧 `watermark_text_test.dart` 8 条、
> 电脑端 `WatermarkTests` 13 条（含**端到端那一帧**：本机 ffmpeg 渲两次比大小，
> 30 KB vs 6 KB —— 证明「会画」，不证明「画得好看」）。

## 1.28 ★ 交付原视频（2026-09-27 新做，规格 §3.7）

**分享 = 把原视频**原样**交出去**：不转码、不压缩、不裁剪，也没有链接、没有自证图。
手机端做两件事：**存进系统相册** → **弹系统分享面板**。

⚠️ 顺带记一句后果（规格 §3.6.6 点名要求写出来）：**面单上的姓名、电话、地址
会原样跟着视频出去** —— 打码整条不做，这是需求方的选择。**不要**在验收时
把它当成漏做，也不许有人「顺手补上」。

### ① ★★ 一键两步：进了相册、也弹出了分享

- 备份页选一条 → 点右边那个**分享图标**（↗）
- ✅ **先弹系统的权限询问**（第一次用）：允许之后
- ✅ 弹出**系统分享面板**（微信 / 邮件 / 隔空投送…都在里面）
- ✅ 分享面板**收掉之后**，去系统相册里看 → **那段录像在里面**
- ⚠️ 顺序反了（先弹分享、相册里却没有）说明只做了第二步

### ② ★ 拒掉相册权限时要说得出原因

- 系统设置里把相册权限**关掉**（或者第一次就问的时候点「不允许」）→ 再点分享
- ✅ App 里出现一句话，大意是**「没有相册权限。去系统设置里给这个应用打开「照片」」**
- ⚠️ **点了没反应是最坏的结果** —— 用户会以为功能坏了

### ③ ★★ 本地副本不在时，先从电脑端取回来

**这一条是「只在归档层就先取回本地」那条规格的验收动作。**

- 先按 §1.24 把某一条**从手机上删掉**（电脑端上那份还在）
- 再点那一条的**分享** → ✅ 它应当**自己从电脑端取回来**（列表上出现
  「正在从电脑端取回来…」），然后照常进相册 + 弹分享
- ⚠️ **电脑端关着**时点它 → 应当说清「取不回来」+ 原因，而不是一个转圈

### ④ ★ 交出去的是**原件**

- 把相册里那一段与电脑端归档目录里那一份**比一比大小**（或者算哈希）
- ✅ **一模一样**（不转码、不压缩、不裁剪 —— 大小差一点点都是错的）
- ⚠️ 顺手确认水印还在（§1.26）：交付件也带着那两行

### 本次**没能自动验证**的（只能真机看）

| 项 | 为什么 |
|---|---|
| **相册那一步通不通** | iOS 要 `PHPhotoLibrary`（权限、Info.plist 的 `NSPhotoLibraryAddUsageDescription`）、安卓走 `MediaStore`（10 以下还要存储权限，而清单里没有它）—— **全是平台能力，本机一样都验不了** |
| **分享面板弹不弹得出来** | 同上；而且「弹出来了但什么都没有」在模拟器上也不一定复现 |
| **从电脑端取回**那一跳 | 要真机 + 真电脑端（走的是回放页那个 `/media/{evidenceId}`） |
| 交出去的那份是不是原件 | 判据是文件比对，只能在真机上做 |

> ✅ 能自动测的那部分**没有新增**（这一批两端都是「调系统 API」）——
> 如实说：**这一条整个只有真机能验**。

## 1.29 ★ 机位满了（2026-09-27 新做，规格 §3.9 / `04-许可设计.md` §5.1）

**许可整套在电脑端**（机器码、激活码都在那边 —— 电脑端有它自己的一份验收动作）。
手机端这一刀只有一件事：**认得出「机位满了」这个码，并把下一步说清楚**。

⚠️ 手机上这句话说的是**去电脑端激活或升级**，不是「连接失败」、也不是「再试一次」——
验收时要盯的正是这一点：用户看到它，应当知道**该去动电脑端**。

### ① ★ 第 N+1 台接不进来

前置：电脑端激活一个 **2 机位**的码（`--slots 2`），并且**已经接了 2 台手机**。

- 第 3 台手机扫码连接 → ✅ 手机上进网的界面出现一句话，大意是
  「**电脑端的机位已经满了**……请在电脑端的【许可】里激活或升级」
- ✅ 而且**最后半句**也在：「已经在用的手机不受影响」
- ⚠️ 电脑端那边**不该**弹出「有一台设备想连进来」的批准弹窗 ——
  机位满了的请求压根不记（否则用户点了同意，屏幕上却什么都没发生）
- ⚠️ 出现的是「连不上电脑端 / 网络错误 / 再试一次」→ **是错的**（那三种是别的码）

### ② ★★ 已经在录的那两台**不受影响**

- 上面第 3 台被挡下之后，回到**第 1 台**那边 → ✅ 它照常录、照常上传备份
- ⚠️ 这一条是 **L5 / L8** 的验收动作：许可只挡**新的**接入，
  已在线的**不打断**。它被挡下来的表现会很安静（那台手机的备份悄悄不传了）

### ③ 同一台手机**重新配对**不受机位限制

- 把第 2 台手机上的 App **删掉重装**（凭据没了）→ 再扫一次码
- ✅ **接得进来**（它占的是**已有的**那个机位，不是新的一台）
- ⚠️ 这一条**必须能过**：过不了的话「机位满了之后手机丢了」就是死局，
  而用户手里那个激活码明明是够的

### 本次**没能自动验证**的（只能真机看）

| 项 | 为什么 |
|---|---|
| 上面三条**通不通** | 它们要「两台真手机 + 一台激活过的真电脑端」，本机凑不出来 |
| 提示的**措辞**在真手机上读起来清不清楚 | 单测只钉住了码与那句话的映射（`upload_protocol.dart`），**排版与截断只能肉眼看** |
| **机器码 / 激活码那半边** | 在**电脑端**（要真 WMI 读得到、要真激活一次）—— 见电脑端 `docs/实现决策.md` §47.10 |

> ✅ 能自动测的那部分：`seat_limit` 这个码与它的 `userHint`
> （`upload_protocol.dart` 的 switch 有测试覆盖），以及电脑端那边的
> 机位计数与拒绝（`DeviceSeatLimitTests` 7 条）。
> **接线与观感只能真机看** —— 如实说：这一条的**界面那半**没有自动化。

## 1.30 ★ 备份页照需求方草图重做（2026-09-27 新做，见 `实现决策.md` §46）

这一版把备份页整个重画了一遍：三张统计卡、电脑备份卡、筛选胶囊、
行上只剩状态小标与 `›`、三个操作搬进新的**录像详情页**、【管理】进批量模式、
右上角垃圾桶 = **断开配对**。

⚠️ 本机已经验到的是**判定与措辞**那两层（640 条测试，其中 30 条是这一版新增的）；
下面这些**只有真机**才看得到。

### ① ★★ 断开配对那个垃圾桶：**录像一条都不能少**

在做任何别的动作之前，**先记下「视频记录（共 N 条）」那个 N 和总占用**。

- 点电脑备份卡右上角那个垃圾桶 → 弹窗第一句应当是
  「断开和这台电脑端的配对？」，正文里要有「手机上录的、电脑上存着的录像，一条都不动」
- 点【断开配对】→ ✅ 状态变成「未配对」，出现【扫码连接】/【填电脑端地址】
- ✅ **回去看那个 N 与总占用：一个都没变**
- ⚠️ 这一条是本批**最该盯**的：那个图标离「删录像」太近，而它一旦真的删了东西，
  用户是**看不出来**的（他以为只是断了个连接）
- ⚠️ 断开之后**下次上传必须要求重新扫码**（契约 §1.1 步骤 4：凭据丢了要重新入网，
  **不得降级为免凭据**）

### ② ★ 三个操作搬进了详情页，而且删不成要留在原地

- 点任意一行 → ✅ 进「录像详情」，看到：单号、来源胶囊（发货视频 / 退货视频）、
  备份状态、录像时间、时长、大小、分段、手机上的路径、那块预览图
- ✅ 底部三个按钮：锁定这一条 / 存相册并分享 / 删除这一条
- 点【锁定这一条】→ ✅ 回到列表，那一行的状态变成「已锁定」
- 点【删除这一条】：
  - **已备份的** ⇒ 两选一（确认 / 取消）
  - **未备份的** ⇒ 三选一，而且必须写着「**唯一一份**」
  - ⚠️ **回查没过或问不到电脑端时** ⇒ 详情页**不关**，只弹一句为什么。
    如果它一闪就关了、录像还在 → **是错的**（那正是这一版最容易写反的一处）
- ⚠️ 底部那句「分享出去的是原视频，没有转码、**没有打码** —— 面单上的姓名、电话、
  地址会原样跟着出去」**必须看得见**（§3.6.6：打码整条不做，不能让用户以为系统替他处理过）

### ③ ★★ 【管理】批量：筛选一变，勾选**必须清空**

- 点【管理】→ 每行前面出现勾选框，上面出现全选 / 已选 N 条 / 批量锁定 / 批量删除
- 勾两条 → 点【批量删除】→ ✅ 弹窗说清「这 2 条 / 多大」，并点明「电脑端那份不动」
- ⚠️ **然后试这个**：勾上一条 → **换一下筛选（来源或日期）** → 回来看勾选框
  - ✅ 一个都不该是勾着的
  - ❌ 如果还勾着 → **是错的**：屏幕上剩下的三条，删掉的会是四条
    （勾选态与筛选是两件事，而用户只能看见其中一件）
- ⚠️ 整批里**只要有一条不能删**（回查说那份没了、或问不到电脑端）⇒
  **一条都不许删**，而且弹窗要**逐条**说清是哪一条、为什么
- ⚠️ 批量删除的弹窗里**不该有【重新上传】**（单条删除里才有 —— 那是 §3.5.6 ② 的三选一）

### ④ ★ 统计卡与窄屏

- 三张卡（本机今日 / 本机全部 / 总占用）**一样高**，且「总占用」那个数字带单位
  （`3.2 GB`，单位不能被截断成 `3.2 G`）
- ⚠️ **在最小号的手机上**（窄屏）+ **系统字体调到最大** → 这一页不溢出、不报黄黑条

## 1.32 ★ 删掉的录像要从列表上消失（2026-09-28，见 `实现决策.md` §48）

需求方 2026-09-28 报的「删不掉」。**根因不是试用期**：删录像删的是**文件**，
而列表是从**索引**归并出来的，索引只增不减（追加写，规格 §6.2）——
所以文件真没了、而列表还在、数字不变、详情页也不返回。
**任何用户都会碰到**，试用用户传不上去、没别的办法腾空间，撞得最狠。

⚠️ 这一批**本机测不到**接线（`recorder_page` 在 widget 测试里 `_sessions` 恒空，
三处注释都写了）。本机验的是它调的那几个**纯函数**（655 条测试，其中 9 条是
这一版新增的）；**下面每一条都只有真机能验**。

### ① ★★ 三处必须**一起**变（本批的正主）

录一条（或者挑一条已有的），记住这三个数字，然后删掉它：

| 看哪 | 在哪 |
|---|---|
| 列表里那一条 | 备份页列表 |
| 「本机全部」那个数 | 三张统计卡中间那张 |
| 「N 个未备份」（如果有） | 同上，或列表顶部那行 |

- ✅ 列表里那一条**没了**（不是变成 0 秒、也不是还在那儿）
- ✅ 「本机全部」**减 1**
- ✅ 总占用**跟着降**（降的幅度约等于那条的大小；有孤儿片段时可能略有出入，正常）
- ❌ **列表没了而数字不变**（或反过来）→ **是错的**，这一批就是来修这个的

⚠️ 只删掉一条里的**一段**（一次录制有几个分段时）时，**那一行不该整条消失** ——
应当是它的「N 段」和时长跟着变小。整条消失才是错的。

### ② ★ 删到最后一条：空态

把列表清空：

- ✅ 出现空态文案（不是一片空白、也不是一个转圈转到底）
- ✅ 「本机全部」是 `0`
- ✅ **杀掉 App 重开**，列表**仍然是空的** —— 这条最要紧：
  索引还在盘上（它只增不减），列表必须仍然按盘上的事实显示。
  ❌ 重开之后删掉的那些**又冒出来** → 是错的

### ③ ★★ 电脑端关着时那条出路（本批新增的能力）

前提：一条**已经备份过**的录像，然后把**电脑端关掉**（或断网），再去删它。

- ✅ 弹的是**拒绝**那个窗：标题「这条现在不能删」，正文说清「现在问不到电脑端」
- ✅ 窗里有**两颗**按钮：「知道了」与「**我确认电脑上有，仍然删除**」
- ✅ 两颗的文案**明显不是一回事** ——
  ❌ 如果那颗按钮也叫「确认删除」→ 是错的：它会让用户以为自己按的是
  平常那个核对过了的确认（规格 §3.5.6② 那两个窗的前提在这里**都不成立**）
- 点「我确认电脑上有，仍然删除」：
  - ✅ 录像**真的从列表上没了**，「本机全部」减 1（**不是**「显示删成功、
    而文件还在」—— 改判时要是照抄了拒绝那颗 plan 的**空** `evidenceIds`，
    就会一段都删不着而界面走完成功流程，见 `实现决策.md` §48.5）
  - ✅ 审计流水里那条的理由**写明了是用户自己确认的**（不是一句普通的删除理由）——
    规格 §3.5.5/④ 要事后答得出「这条为什么没了」
- 点「知道了」：**什么都不该变**

### ④ ★★ 「查不了」与「那份没了」给的路**不一样**

- 电脑端**开着**，但归档层上那一份**被删掉了** → 拒绝窗里**只有「知道了」**，
  **没有**那条出路（❌ 有就是错的：那是**问到了**的答案「没有这一份」，
  手机上这条真是最后一份，不该让用户凭一句「我确认」跨过去 —— I2）
- 电脑端**关着** → 有那条出路（见 ③）

两种拒绝的正文也**必须不一样**：混成一句的话，用户会以为「电脑开着就能删了」，
而其实可能是那份真没了。

### ⑤ ★ 批量删除**没有**那条出路（**故意的，别当漏做**）

进【管理】批选几条（其中至少一条是「查不了」的那种），点删除：

- ✅ 弹的还是那句「一条都不能删，所以这一批**一条都不会删**」
- ✅ **没有**「我确认电脑上有」那颗按钮
- 理由：一批里可能几条是「那份没了」，用户记住的是「我删了 10 条」，
  留在盘上那几条会变成他以为早就没的东西。要腾空间可以**一条一条删**。

| 项 | 为什么 |
|---|---|
| ① 三处一起变 | 页面在 widget 测试里够不着（`_sessions` 恒空，要 `path_provider` 平台通道） |

### ① ★★★ 语音提示 + 录制声音**同时开**，播报会不会被录进去 / 会不会哑掉

**这是本批唯一一个连方向都预判不了的行为**，所以排第一。

前提：设置里把 `语音提示` 和 `录制声音` **两张卡都打开**。

- 开始工作 → 听：**播报还出得来吗**（❌ 哑了就是错的：`AVCaptureSession`
  一碰麦克风就改 `AVAudioSession` 的语义，iOS 上极可能把 TTS 掐掉）
- 录一段 → 把文件导出来**用耳机听**：
  - 听得到现场的说话声（说明音轨真的接上了）
  - ⚠️ **听不听得到播报声**，这一条**两种结果都要记下来**（不是对错，
    是事实）：录进去 → 记「播报会被录入」；听不到 → 记「播报不被录入」。
    两种都能接受，**但必须知道是哪种**，因为将来用户会问
- 安卓同样跑一遍（两端用的不是同一套音频栈，结果**可能不一样**）

做的时候用的是 `.playAndRecord` + `.defaultToSpeaker`，
⚠️ **没有**用 `.mixWithOthers`（那会把别的 App 的音频混进来）。

### ② ★★ 录出来的文件**确实有音轨**（两端各一条）

`录制声音` 开着，录一段，把文件从手机里导出来：

- iOS：`ffprobe` 或「显示简介」里能看到 **2 条流**（视频 + 音频，AAC 单声道 44.1k）
- 安卓：同样看得到 2 条流
- ✅ 放出来**有声音**（不是一条静音的空轨）
  ⚠️ 「有音轨但是全程静音」是最可能的失败样子：`addTrack` 成了、
  但样本一个都没写进去 —— **光看属性看不出来，必须听**

### ③ ★ 关掉开关后**确实没有音轨**

`录制声音` 关掉，录一段：

- ✅ 放出来**没有声音**
- ✅ 文件里**只有 1 条流**（❌ 还有音轨那条空轨就是错的 ——
  说明「关了」只关掉了画面上的开关）

### ④ ★★ 安卓**第二段及以后**还有没有声音

安卓是**分段**录的（轮转会产生第 2、3… 段），每段一个新封装器。
**只听第一段会漏掉这个 bug。**

- 录一段**足够长、跨过一次轮转**的（或者把分段时长调短），然后把
  **每一段**都翻出来听：
  - ✅ **每一段都有声音**
  - ❌ 第一段有声、后面全哑 → 是错的（新封装器要从音频 format 建轨，
    而那份 format 只来一次 —— 见 `实现决策.md` §49.6）
- ⚠️ 这个 bug **不看文件属性根本发现不了**（轨在、时间戳正常，就是没声音）

### ⑤ ★★ 停止录像**会不会卡住不回**

- 录一段带声音的，点【停止】
- ✅ 几秒内回到界面
- ❌ 一直转圈 / 卡死 → 是错的：轮转时要**两个 input 都 `markAsFinished()`**，

  （见 `实现决策.md` §49.6）
- ⚠️ 安卓的 `AudioRecord.read` 是阻塞的，停止时要确认**采集线程也跟着停了**

  （录音机 / 微信语音）**还拿不拿得到麦克风**

## 1.34 ★ 实时共享（规格 §3.8，2026-10-01 新做，见 `实现决策.md` §50）

⚠️ **这一整节一行都没上过真机** —— 两端各自的原生实现（iOS 的
`LiveStreamer.swift` / 安卓的 `LiveStreamer.kt`）本机**都跑不了真机**，
iOS 连编都编不了（只有 CI 的 `ios-compile-check.yml`，而它**不挂 push**）。
要两台东西同时在场：一台电脑 + 至少一台手机。

### 怎么做

1. 设置 →【实时共享】打开 → **退出设置** → 进发货栏 → 点【开始工作】。
2. 电脑端顶栏点【实时多画面】。
3. 扫几件发货、几件退货。
4. 双击电脑端某一格进全屏，换 720P / 1080P。
5. **在录着的时候**把手机拿远（断开 Wi-Fi）再拿回来。
6. 录完一段，打开那段录像看水印。

### 判据

- ⭐ **电脑端那一格出画面**（这是整条链路唯一的当场凭据）。
  ⚠️ 安卓上画面**可能是躺着的**（手机推的是传感器方向的裸流，
  而裸流没有容器能带旋转信息）—— 用电脑端那一格右上角的**转动按钮**转一下即可，
  **那不是 bug**；iOS 那边因为是会话级旋转，出来就是正的。
- ⭐ **F / T 那对数与手机上扫的对得上**，且**跨零点会自己归零**
  （北京时间自然日，§50.5）。
- ⭐ **`F` / `T` 不进视频水印**（第 6 步：水印里只有时间与单号）。
- ⭐ **推流绝不影响录像**（第 5 步）：断网/重连期间手机上那段录像**连续不掉段**，
  电脑端那一格黑掉或写着原因都行 —— 而**录像不能有任何缺失**。
- ⭐ 关掉开关之后那一格**立刻**变「无信号输入」（关是立刻的）；
  **重新打开要等下次【开始工作】**，而且设置页那张卡上要能看到这句话
  （§50.3 —— 这个「等下次」是刻意的，不是坏了）。
- ⭐ 电脑端要 720P / 1080P 时，**iOS 会换、安卓会如实拒绝**
  （§50.4）；两边都不许出现「电脑端显示已切到 1080P、而画面没变」。
- 录制吃紧（过热/低电量/存储将满）时推流**被自动停掉**，且设置页那张卡
  写着**为什么停**（§50.2 第 3 条）。

### 不通过时看哪

`实现决策.md` §50.2（三条隔离规则）、§50.3（为什么不是立刻生效）、
§50.4（安卓的档位）、§50.6（那条 INTERNET 权限）；
电脑端 `docs/真机验收清单.md` §22。

## 1.39 ★ 写失败要看得见（2026-10-05，T22 取证）

改造清单 T22：**写样本失败原来只有一条原生日志**（Kotlin 的 `android.util.Log`
只进 logcat、**到不了诊断包**；Swift 那条在 `AVAssetWriter` 的失败态上**根本没报**）
⇒ 正在丢证据，而用户在界面上什么都看不到。

**改了什么**：两端的写失败都走**已有的**上报路径（`RecorderEvent.Failed` /
`.failed`，与「开新分段失败」同一条）：**不停录**，但会记一条日志 + 让界面挂一条可见的失败记录。
⚠️ **带节流**：坏掉之后是每一帧都失败，30 fps 原样上报会刷满环形日志
（那比不报还糟——被挤掉的正是别处的线索）。所以**头一次立刻报**，
之后每 10 秒最多一条，**每条都带累计次数**。

| # | 项 | 判据（一句话） |
|---|---|---|
| ① | **安卓：写失败能看到** | 录制中日志（`事件 ▸` 抽屉 / 诊断包）里出现一行 `原生`：`写入封装器失败：…（累计 N 次）`，且**录制没有停**；界面上也挂出了这条失败（`onNativeFailure` 那条路） |
| ② | **iOS：整段写坏要能看到** | 若某一段的 writer 落进 `.failed`，收尾那一刻会有一条 `这一分段写失败，整段没进收尾` —— 而**这一段既不会进收尾、也不会有任何记录**，所以这条是它唯一的存在痕迹 |
| ③ | **节流确实在** | 一直坏着的话，10 秒内**不会**出现第二条同类记录；每条末尾的 `累计 N 次` 在涨 |

⚠️ **本机验不了「有一帧真的失败」这件事**：
- 本机没有原生测试设施（`android/app/src/test` 不存在、`ios/RunnerTests` 是 Flutter 空模板），
  清单原文要求的「注入一个会失败的 writer」在 Windows 上做不到；
- Swift 在 Windows 上**根本编不了**，`ios/` 那半边只能靠 CI 出包时证明编得过；
- Kotlin 这半边本机只跑了 `flutter build apk --debug`（**证明编得过**）。

⚠️ 所以本机**验到的是**：Dart 侧那条接收路径是通的且有覆盖 ——
`test/recording_coordinator_test.dart` 的 `原生报错会被记下来并可读` 已断言
`RecorderFailedEvent` ⇒ `coordinator.lastError` + `onNativeFailure` 都被填上
（「原生错误必须让用户看见，不能静默」）。**原生真的会发出这个事件**只有真机答得上来。

|---|---|---|
| ① | **安卓** | 录制中强杀 App（开发设置里「强行停止」或 `adb shell am force-stop`）→ 重启 → 日志里有一行 `录制`：`… 有 1 段没登记的分段救不回来（…）：segment-001.mp4` |
| ② | **iOS** | 同上，从 Xcode 的设备控制台或「事件 ▸」抽屉里看同一行 |
| ③ | **反过来别误报** | 正常停录的那一场**不该**有这一行（正常停录时那一段是登记过的） |

⚠️ 本机验不到「真的被杀」：`test/session_finalizer_test.dart` 的 `T20 没登记的分段`
三条例用**造出来的文件**验的是「扫得出来、该报的报、不该报的不报」，
**「真被杀之后盘上剩的是不是这个形状」只有真机答得上来**。

## 2. 顺手记的东西

验收时如果出现**编译全绿但行为不对**的情况，请把这几样记下来：

- 事件列表里的原文（**在「事件 ▸」抽屉里**，采集页底部）
- 采集页顶部那行诊断计数（`工作区 N（未收尾 M）· 索引 K · 打点 P`）
- 是在哪一步、什么模式下出的
- **设置没存住**的话，把 `settings.json` 原文抄下来（`<documents>/vidlog/settings.json`，
  在 Files App 里 App 自己的目录下，跟 `index.jsonl` 同一层）——
  它能直接区分「写的时候就没写对」和「读的时候没认出来」
- 如果能拿到，`flutter logs` 或 Xcode 的设备控制台输出

这些是修 bug 时唯一有用的线索。真机上出的问题**大概率**在原生层
（相机时序、编码器与封装器的配合、轮转），而 Dart 侧的逻辑都已经有测试覆盖。

## 3. 已知的、还没做的

| 项 | 影响 |
|---|---|
| **安卓整条链路未上真机** | 2026-09-23 已接上（`实现决策.md` §23）：通道改名、相机预览、条码解码、滴声都实现了，APK 也编得过。**但一行都没在真机上跑过** —— 相机时序、预览矩阵、识码坐标换算全是纸面推导 |
| **二维码在录制页仍然不开**（**故意的**） | 2026-09-26 起二维码识别**只在扫码连接那一屏**开（规格 §3.4.5 ④），录制页仍然只认一维码 —— 面单上或环境里的二维码不该被当成单号。若将来面单真要用二维码，得先做各家承运商的载荷解析（**从 URL 里抽单号**，那是另一件事） |
| 按设备记忆变焦倍率 | 规格原文是「**建议**」。现在只在本次工作期间保持，退出 App 就回 1 倍 |
| **设置改了当段不生效** | 模式和档位是编排器的构造参数，只在「开始工作」时重建。**这是有意的**（工作途中重建会把相机和界面状态拆开，见 `实现决策.md` §17.3），界面已明说。要真做成立刻生效，得先解决「新编排器 `isWorking` 是 false 而相机开着」那个态 |
| **保留期：设置能选，但选了不会删** | 下拉两端都做了（**发货 / 退货各一份**，规格 §3.5.2.1）。⚠️ **但执行层两端都没接线** —— 没有触发点；而归档层 = 电脑端本机磁盘时，规格 §3.5.1 要求不给清理选项 ⇒ **现在选哪个档位都不会删任何文件**，两端设置页上都把这句话写出来了。电脑端的**判定层**有（`CleanupPlanner.PlanPerBusinessType`）；手机端**没有**，当初的理由是「起算点是 M5 的产物」—— ⚠️ **M5 已经把它产出来了**（`ArchiveRecord.timeAnchor`），这条理由不再成立 |
| **标签表跨端互通只验过代码、没验过真机** | 手机端与电脑端写的是同一份形态（同文件名、同位置、同键名 `EvidenceId`/`Key`/`Value`/`UpdatedAt`、同取值），但这是**读代码**核出来的。真正的验证只有一条：**把手机端导出的 `labels.jsonl` 拿到电脑端打开，看它认不认** |
| 手机端标签只写不读 | `LabelStore.loadAll()` 那一半已经有了，但**界面上仍然没有任何地方显示它**。不影响正确性，纯粹是没需求 |
| **手机端本地回放** | 没有。录下来的东西在手机上只能在「文件」App 里看到文件。（**电脑端的网页回放是有的** —— `PlaybackServer` 的 `/`，M3 起就在） |

第 1 条要特别注意：**它是一个「编译期看不出来」的坑的现役版本**。
安卓那半边编译全绿、CI 全绿 —— 而这恰恰是重点：
上一个版本（通道名字对不上）也是编译全绿，运行时每一次调用却都返回
`notImplemented`。现在轮到**预览矩阵**和**识码坐标换算**这两处：
它们同样只在真机上有对错。详细原因见 `实现决策.md` §23。
