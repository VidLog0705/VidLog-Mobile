## 1. 「扫码静止停录」的停止条件

规格 §3.3.1 的这一行只出现了一次，术语表也没定义「离场 / 入场」：

> | 扫码静止停录 | 首次识别到单号 | 同码离场后再入场并静止达设定时长 |

**已向需求方确认**：指的是**真实的视觉目标跟踪** ——
扫到的那件包裹先**离开取景框**，随后又**回到画面**，然后静止达设定时长。

```
扫 A 开录
  ↓
包裹 A 离开取景框   ← 需要识别「离开的是哪个东西」，不是画面差分
  ↓
包裹 A 回到取景框
  ↓
静止 N 分钟  → 停
```

**职责切分**：原生层做目标跟踪并产出
`TrackedPackageLeft` / `TrackedPackageEntered` 事件，
**停录状态机只消费事件**。所以停录逻辑能在 Dart 里完整测到，
不需要真机就能验「离场 → 入场 → 静止 → 停」这条链。

**静止时钟从「入场」那一刻重新计**，不是从入场前那次活动算 ——
规格要的是「离场后再入场**并**静止达设定时长」。

### ⚠️ 1.1 规格里一处前后不一致（实现取了其中一个读法）

| 出处 | 说法 |
|---|---|
| §3.3.1 的「停止录制」列 | 扫码静止停录 = 「同码离场后再入场并静止达设定时长」，**没提复扫** |
| §3.3.2 错码保护的标题 | 「**同码停 / 扫码静止停录 两个模式都启用**」，规则是「二次扫描**只有单号相同才停止**」 |

按 §3.3.2 的字面，**扫码静止停录模式下复扫同码也会停**。

**本实现取了 §3.3.2 的读法**（复扫也停）。改动只需一行：
`lib/recording/work_mode.dart` 里 `scanThenStaticStop` 的
`stopsOnSameWaybillRescan` 改成 `false` —— 收尾逻辑不用动，有测试锁着。

## 2. 三种停录机制与它们的优先级

| 机制 | 规格 | 生效范围 |
|---|---|---|
| 同码复扫 | §3.3.2 | 同码停、扫码静止停录 |
| 画面静止 | §3.3.3 | 全部（可设为「关闭」） |
| 时长兜底 | §3.3.4 | **全部，含「关闭」档** |

**三种会同时满足**，所以：

- 每个机制都有**独立的一组测试**，验其中一个时把另外两个隔离掉
  （测试里的 `isolated()` / `durationOnly()` 两个辅助函数就是干这个的）。
- 同时满足时的优先级：**静止 > 时长兜底**。静止是更具体的信号，
  报出来的原因对用户更有用。
- **资源告警不等时间**，一旦上报立即收尾。

### 2.1 静止封顶（§3.3.3 / 不变量 I12）的实现

规格原文：

> **强制约束**：静止判定必须**按"本次已录时长"封顶**
> 原因：若不加封顶，长时间无人后一开录，会立刻被判"已静止超时"而当场停掉

实现方式：**静止时钟的起点被钳在开录时刻**（`lastMotionAt` 在开录时置为开录时刻）。

之所以等价：设 `measured = now - staticSince`、`elapsed = now - startedAt`，
规格要的「静止时长按已录时长封顶」是 `min(measured, elapsed) >= 阈值`，
而它等价于 `now - max(staticSince, startedAt) >= 阈值` —— 就是把起点钳一下。

两条都验了：

- 正常静止 → 到设定时长停
- **架机 30 分钟无人后再开录 → 不是立刻停，而是录满设定时长才停**（M4 验收项）

### 2.2 时长兜底（§3.3.4）的状态

```
录制中 ──4 分钟──> 语音 + 两个按钮【停止】【继续】
                      │
          ┌───────────┼─────────────┐
      点【停止】   点【继续】    1 分钟无操作
          │           │             │
       立即停止   取消本轮上限    默认继续
                  再过 5 分钟       ──> 停止
                  再次询问（循环）
```

「无操作」与「主动继续」是两回事：前者代表用户不在场（兜底生效），
后者代表用户在场且明确要继续（不误停）。

## 3. 取景框（§3.2.2）

规格：**只有框内的面单会被识别，框外一律忽略**，防止扫到画面里其他包裹的面单。

**判据：检测框的中心点落在取景框内。**

- 不用「整框都在里面」：面单举得离镜头近时边角常探出框外，
  要求整框在内会让用户反复调整距离 —— 那正是这个功能最不该造成的负担。
- 不用「重叠面积过半」：面积判据在面单只露出一角时行为不稳定。
- 中心点判据隐含了「每个轴上至少一半重叠」，几何上好解释也好测。
- 规格要防的是「画面里**其他包裹**的面单」，那些的中心点天然在框外。

用**归一化坐标**（0~1 的画面比例）而不是像素：换设备、换预览尺寸都不用改参数。
框本身是正方形，所以在归一化坐标里宽高不相等 —— 有测试按像素验这一点。

框大小提供三档预设（§3.2.2「至少提供预设档位」）。

## 4. 录制会话与孤儿收尾（§3.1.1 / I9）

结构与电脑端一致，且**跨端契约相同**（母仓 `docs/02-数据模型.md`）：

- 工作区：`<root>/<sessionId>/session.json` + 分段文件 + 收尾后的 `finalized.json`
- **孤儿 = 有 `session.json` 但没有 `finalized.json`**
- `SessionFinalizer` 只有一个公开入口，**所有停录原因走同一条路**（I9）
- `OrphanRecovery` 没有自己的收尾逻辑，只是换了个 `StopTrigger.processKilled`

### 4.1 与电脑端的差异（刻意的）

| 项 | 电脑端 | 手机端 |
|---|---|---|
| 中间容器 | 录制期 MKV，停止后 remux 成 MP4 | **无** —— 原生相机直接写最终 MP4 |
| 成品校验 | FFmpeg 真解一遍（§3.1.4） | **无**（见下） |
| 内容哈希 | SHA-256 | SHA-256 |

**为什么手机端没有 remux**：原生相机（MediaCodec / AVAssetWriter）写的就是最终容器，
少一次 remux 就少一次「收尾到一半磁盘满了」的机会。

### ⚠️ 4.2 手机端没有「实际解码校验」—— 一处已知的验证强度差异

电脑端用 FFmpeg 真解一遍成品来确认可播（规格 §3.1.4）。**手机端没有 FFmpeg**，
这里只能依赖原生录制器自己的收尾结果。

这意味着「分段文件存在且非空」不等于「能播」。规格 §8 点名要防的
「不产生无法播放的半成品」在手机端**只做到了弱保证**。补的办法有两条，
都需要真机或额外的原生代码：

1. 原生层在收尾时用系统解码器做一次首尾帧抽检
2. 真机回归时人工确认

## 5. 「写入索引失败」也算收尾失败

`FinalizedSegment.isPublished` = 算过哈希 **且** 已写入索引 **且** 无失败原因。

**写索引失败也算失败**：文件在盘上、哈希也对，但用户检索不到 ——
那对「找得到自己的证据」这个承诺等于没入库。

> 电脑端在 M2 时踩过这个坑（`IsPublished` 漏了失败判据，索引写失败的会话被标成
> 「已入库」，是测试抓到的）。手机端从一开始就带上这个判据。
